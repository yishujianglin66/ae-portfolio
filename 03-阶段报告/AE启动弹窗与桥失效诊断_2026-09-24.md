# AE 启动弹窗与 Adobe 桥失效诊断（2026-09-24）

## 0. 症状（用户原话）

> "ae每次启动说崩溃，打开后弹出保存文件，每次点击取消就自动退出杀掉ae了"

追认：弹窗是 **"是否保存对 xxx.aep 的更改？"**；入口是 **"脚本/工具调起来的"**（非双击图标或工程）。

## 1. 结论（两条机制，第二条才是"点取消 AE 就关闭"的直接原因）

**AE 没有崩溃。** 有两条互相独立的机制会把 AE 弄成"弹保存框 → 点取消 → AE 关闭"：

**机制 A：本仓脚本强杀 AE**（§2 证据 7）。工具下发命令 → 桥不认 → 工具等超时 → `taskkill /F`。
AE 停在保存确认框上时被强杀，看起来就是"点取消 AE 被杀"。

**机制 B（直接命中，且是复发原因）：测试目录里的"脚本式文件"会在被 pytest 收集时拉起 AE GUI。**

- `tests/quick_render_test.py`：模块级 `sys.exit(main())`，而 `main()` 里 `AfterFX.exe -r` **创建工程**；
- `tests/direct_render_test.py`：模块级 `subprocess.Popen(...)` 启动 **AfterFX.exe GUI**，末尾 `sys.exit(1)`；
- `pytest.ini` 的 `python_files = test_*.py` **本来不会收集它们**（已实测：标准收集里命中数 0），
  但 **显式把文件路径当参数传给 pytest 会绕过该模式** —— 于是 AE 被拉起、`sys.exit` 把 pytest 打死、
  **AE 带着未保存工程留在桌面上**，用户看到"是否保存对 xxx.aep 的更改?"。

> **责任说明**：2026-09-24 上午那次复发（用户第二次报障）**是我造成的** ——
> 我为了评估"改动波及面"把 253 个测试文件**按路径**传给 pytest，其中就包含了上面两个脚本式文件。
> 该次运行 `no tests ran ... INTERNALERROR ... SystemExit: 1`（16 分钟、0 用例）正是它们干的事。
> 我先前只报了机制 A，漏了机制 B，属于诊断不完整 —— 已在 §5 补上护栏修复。

## 4. 代码改动（全部为防呆/一致性修复，不引入新功能）

1. **修误导文档（11 处注释）**：`ae/scripts/{amv,manga,puppet}/*.jsx` + `ae/textfx_effects.py`
   的用法注释由 `{command:"runScript", args:{code:…}}` 改为
   **`{command:"executeAtomScript", args:{script:…}}`**（与监听器实际读的键一致，见证据 6）。
   残留检查：0 处。
2. **关掉"强杀 AE"（4 处）**：改为**默认不杀**，仅当 `AEKV_ALLOW_FORCE_KILL_AE=1` 时执行；
   未授权时给出明确提示，由后续 `is_ae_running()` 判定为**明确失败**而非破坏性成功。
   顺带把 `run_ae_effects_full.py` 的 `shell=True` 字符串命令改成参数列表。
   **已在真实运行的 AE 上验证**：调用 `stop_ae()` 后 AE 仍存活。
3. **修卸载器 + 卸掉死桥**：`uninstall_bridge` 改为**候选名单**逐个尝试
   （含 `z_mcp_bridge_startup.jsx`），并区分"一个都没找到"与"删失败"；删除方式改为
   **先留档 `.uninstalled.bak` 再移除**。随后**提权卸载**了 AE 里那个失效加载器。
4. **修空壳目录误判（同一缺陷族的第三次出现）**：
   - `detect_installed_adobe_apps`：改为优先选"`startup_subdir` 真实存在"的路径
     （与 `get_startup_dir` 判据一致），都不满足才退回存在性判断并告警。
     **实测：修复后正确解析到 AE 2025 的 Startup 目录，并成功找到那个加载器。**
   - `tools/unified_tool_integrator.get_install_path`：原为**裸读配置零校验**，
     现要求**配到真实可执行文件**才算数，验不过回退 `core.adobe_discovery`（本仓单一真相源），
     仍找不到则返回空串让下游诚实降级。
   - `tool_config.json`：`search_paths.adobe` 5 条**全指向 2026**（AE 2026 是空壳、PR/PS/AI/ME 的 2026
     目录根本不存在），按实测重写为真实存在的 2025 系列（Illustrator 两个年份都不存在故移除），
     并写入 `_note_adobe` 说明权威来源。
   - 保留项：`core/adobe_discovery.py` 与 `tools/toolchain_manager.py` 里的 2026 候选**保留不动**——
     它们**带可执行文件存在性校验**，会正确跳过空壳（这类"多候选 + 校验"是安全写法）。
5. **修参数键不一致（证据 6）**：`ae/ae_command_client.py`（2 处）与 `ae/ae_mcp_client.py`（2 处）
   由只发 `{"scriptContent": …}` 改为**双键** `{"script": …, "scriptContent": …}`，
   与唯一跑得通的 `ai/ae_render_channel.py:141` 一致。
   （`ae/ps_mcp_client.py` 的 `scriptContent` 属 **Photoshop** 通道，与 AE 监听器无关，未动。）
6. **脚本式文件 import 护栏（7 个）**：见 §5。

## 5. 补修：脚本式文件的 import 护栏（机制 B 的根治）

给**7 个**脚本式文件加了**被 import 即失败**的守卫（用 `python tests/<file>.py` 直接运行时行为不变）：

```python
if __name__ != "__main__":
    raise ImportError("这是脚本而非 pytest 用例，请用 `python tests/<file>.py` 直接运行；"
                      "不要用 pytest 指定该文件路径（会拉起 AE）。")
```

| 文件 | 模块级副作用（加护栏前） |
|------|----------------------|
| `tests/direct_render_test.py` | `subprocess.Popen` 启动 **AfterFX GUI** |
| `tests/quick_render_test.py` | `AfterFX.exe -r` **创建工程** |
| `tests/e2e_aerender_real.py` | 同类脚本式副作用 |
| `tests/test_davinci_api.py` | `subprocess.Popen` 启动 **DaVinci Resolve GUI** |
| `tests/test_cookie_read.py` | `requests.get` **外连抖音且携带 cookie** |
| `tests/test_davinci_dll.py` | `subprocess.run` tasklist 探测 |
| `tests/test_preview_inheritance.py` | `sys.exit(1)` **直接杀死 pytest 进程** |

**决定性验证**（用原来那个引发事故的调用方式，一次性传入全部 7 个文件）：

```
验证前 AfterFX 进程数 = 1（用户自己在用）
pytest <7 个文件路径>  → 7 个 ImportError，消息明确指向 `python tests/<f>.py`
验证后 AfterFX 进程数 = 1        ← **没有新增 AE 进程** ✓
```

**另一条被实测否掉的思路（记录下来免得后人重走）**：我原想在 `tests/conftest.py` 加
`pytest_ignore_collect()` 让"显式路径"也被忽略。**实测无效** —— 连 pytest 自带的
`--ignore=tests/quick_render_test.py` 都挡不住显式路径（仍报 ImportError）。
故该 hook 已删除，改为在 conftest 里如实写下结论：
**`collect_ignore` / `pytest_ignore_collect` / `--ignore` 三者都挡不住显式路径，
唯一的防护是每个脚本文件自带的守卫。**

**回归确认**：标准收集 `6203 tests collected`、**0 error**；7 个文件在标准收集里命中数 **0**（行为不变）；
AE/Adobe 相关测试 **62 passed**。

> 这与早期计划里的 **P1（`collect_ignore` 的 41 个脚本式测试文件）** 是同一件事的样本：
> 那批文件的共同病根就是"模块级副作用"，**只靠 `collect_ignore` 挡不住显式路径**，
> 必须把副作用搬进函数/加 import 护栏。建议把本护栏模式推广到其余脚本式文件。
