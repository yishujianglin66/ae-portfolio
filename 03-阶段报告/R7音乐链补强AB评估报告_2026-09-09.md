# R7 音乐链补强·A/B 评估报告（2026-09-09）

> 目标（方案 `09-计划文件/2026-09-08_调研驱动推进方案修正.md` R7）：
> Demucs / beat_this / all-in-one / whisperX 四项对比评测，替换或双轨现链。
> 验收线：beat_this vs 现链同口径 beat_hit_rate A/B；结构分段与人工标注一致率 ≥85%。
> 结论性质：**beat_this 假设被实测推翻；all-in-one 遇硬障碍 + 前置缺口；Demucs 可用性确认**

---

## 一、结论速览

| 候选 | 结论 | 处置建议 |
|------|------|---------|
| **beat_this** | 拍点网格更规整，但**偶发漏拍**（间隔翻倍），CV 反而劣于 librosa | **不替换现链**；仅在需要下拍时作为补充 |
| **all-in-one** | 硬依赖 madmom（需 MSVC 编译，环境不可用）；且验收线"人工标注一致率"**无基准** | 暂缓，前置补齐后再评 |
| **Demucs (htdemucs)** | 权重可下、8s 分离成功、产物合理 | 可作 MelBand 的备选 stem 源 |
| **whisperX** | 未评测（歌词锚点规则尚未有需求，见 §四） | 延后 |

**核心发现**：方案"beat_this 精度更优、可替换 madmom/librosa"的假设**不成立**——至少在项目当前的燃向 BGM 语料上，librosa 的节拍检测反而更稳（不丢拍）。

## 二、beat_this vs 现链 A/B（实测）

### 2.1 方法

`scripts/r7_beat_ab.py`：同 BGM 上两法对比，四个维度（互匹配率 / 拍间隔 CV / 推断 BPM / 下拍可用性）。

### 2.2 结果（3 首 BGM）

| BGM | 指标 | librosa | beat_this |
|-----|------|---------|-----------|
| 1_from10s（129 BPM） | 拍数 / CV / 推断BPM | 87 / 0.035 / 129.27 | 88 / 0.0966 / 130.04 |
| 2[高质量]（129 BPM） | 拍数 / CV | 112 / 0.035 | 113 / 0.0966 |
| DiorGoFlex（144 BPM） | 拍数 / CV / 推断BPM | 354 / 0.043 / 144.3 | 321 / **0.355** / **119.28** |

互匹配率均值：librosa→beat_this 0.509 / beat_this→librosa 0.530（两法约一半拍点对不上）。

### 2.3 关键诊断：beat_this 的 CV 为何反而大

看拍间隔分布（`reports/r7_beat_ab.json`）：

| BGM | 方法 | 间隔中位 | p10-p90 |
|-----|------|---------|---------|
| DiorGoFlex | librosa | 0.4179 | 0.395-0.441（**紧凑**） |
| DiorGoFlex | beat_this | 0.4200 | 0.400-**0.840**（**散**） |

**beat_this 中位值很规整（0.42 网格），但偶发出现 0.84 / 1.56 的间隔翻倍/多倍空隙**——即**漏拍**。librosa 从不漏拍（间隔始终 0.37-0.51）。

**判定**：beat_this 的"拍点精度"局部更优（落在网格上的点很准），但**鲁棒性差于 librosa**。对踩点剪辑而言，漏一个拍 = 切点错位一次，是比"拍点微偏"更严重的缺陷。

### 2.4 结构性差异：下拍

| 能力 | librosa 现链 | beat_this |
|------|-------------|-----------|
| 下拍（4/4 第一拍） | ❌ 无 | ✅ 有（88 拍中 22 下拍） |

这是 beat_this **唯一的结构性优势**——下拍正是 R-2026-0002"网格量化锚"需要的输入。但注意：现链的网格量化用的是 16 分音符网格，不是 4/4 下拍，因此该优势当前未被消费。

**处置建议**：不替换。若未来需要下拍驱动的规则（如"下拍必切"），可把 beat_this 作为**仅下拍**的补充通道，而非主节拍检测。

## 三、all-in-one：双重前置缺口

### 3.1 硬障碍：madmom 依赖

`allin1` 导入即需 `madmom`，而 madmom 是 Cython + C 扩展，安装需 **MSVC 14.0 编译**。当前环境（Windows，无 MSVC）无法从源码构建，PyPI 无预编译 wheel。

```
ModuleNotFoundError: No module named 'madmom'
→ pip install madmom → error: Microsoft Visual C++ 14.0 or greater is required
```

### 3.2 验收基准缺失（更根本）

方案验收线是"结构分段与人工标注一致率 ≥85%"，但项目**没有任何结构分段人工标注**：

- `data/rules/ruleset.jsonl` 里 R-2026-0002 的 `bgm_structure` 是**纸面声明**（刚在 R4 才发现它从未被校验）
- `production_director` 的 `bgm_structure` 字段无实际数据源

即：即使装好 all-in-one，也**没有可对比的 gold 基准**。这是方案的前置缺口，需先建结构标注集。

**处置建议**：暂缓。先建结构标注集（人工标注 N 首 BGM 的 intro/build/drop 时间轴），再解决 madmom（或换有预编译 wheel 的结构分段方案）。

## 四、Demucs 可用性确认

| 项 | 结果 |
|---|------|
| 版本 | demucs 4.1.0（随 allin1 安装） |
| 权重 | htdemucs 从 hf-mirror 下载成功（BagOfModels） |
| 分离 | `--two-stems drums` 8s 完成（40.95s 音频） |
| 产物 | drums.wav（mean -23.4 dB）、no_drums.wav |

**价值**：作为 MelBand 的备选 stem 源（现链 MelBand SDR 10.43，Demucs htdemucs 是独立实现，可交叉验证 stem 质量）。但**完整 A/B 需同口径 SDR 评测**（需真值 stem，本项目无），本次仅确认可用性。
