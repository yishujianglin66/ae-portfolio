## 经验 1：AE MCP「自动启动退化」——Startup 机制从未失效

### 反模式（错误归因）

- 现象：AE 启动后 bridge 不消费命令、MCP 工具全部超时。
- **错误归因**：「`app.scheduleTask` 在 Startup 上下文不可用」「轮询机制本身有缺陷」「Startup 自动加载不可靠」→ 进而放弃 bridge，改用 ComputerUse 手动点菜单。

### 真实根因（已实证）

| # | 根因 | 证据 / 机理 |
|---|------|-------------|
| 1 | **`Pref_SCRIPTING_FILE_NETWORK_SECURITY` 权限被置 0** | AE 首选项中「允许脚本写入文件 / 访问网络」开关被关闭。Startup 脚本即使加载成功，一旦尝试 `File.open("w")` 写命令/结果文件即静默失败 → 表现为「bridge 不响应」。重置该权限位为 1 后恢复。 |
| 2 | **AfterEffectsMCP 的 build 指向错误 bridge 目录** | 系统并存多套 bridge 实现（见经验 3），MCP 服务器构建时硬编码的 bridge 路径与实际激活的 Startup 加载器不一致 → 命令写到了「没人监听」的目录。 |
| 3 | 模态对话框阻塞（次要） | 快捷方式错误 / 首选项重建弹窗会阻塞 `scheduleTask`，属环境噪声，非机制缺陷。 |

### 正确做法

1. AE 启动后 bridge 不响应，**先查权限位**，再查 build 路径，**最后才怀疑机制**。
2. 确认 `Edit → Preferences → Scripting & Expressions → Allow Scripts to Write Files and Access Network` 为勾选态（即 `Pref_SCRIPTING_FILE_NETWORK_SECURITY = 1`）。
3. 确认 MCP 服务器写入的命令目录 == Startup 加载器监听的目录（本项目为 `.ae-mcp-bridge/`）。

### 决定性结论

> **Startup 自动加载 + `scheduleTask` 轮询机制本身从未失效。** 本会话 bridge 全程承载了诊断、探测、验证渲染、A/B 测试、Pass 3 生产渲染共计数十条命令，零失败（含单次 98.3 秒渲染），彻底推翻「配额 1–2 条」的旧判断。

### ✅ 检查清单（AE 启动后 bridge 不响应）

- [ ] `Get-Process AfterFX` 确认 AE 已起，等待 ≥60–90s（插件套件大时更久）
- [ ] 检查 `Pref_SCRIPTING_FILE_NETWORK_SECURITY` 是否为 1（首选怀疑对象）
- [ ] 确认 MCP build 的命令目录与 Startup 加载器监听目录一致
- [ ] 确认无模态对话框（MainWindowTitle 非空）
- [ ] 检查 `ae_auto_listener.log` 是否出现 ready 标志
- [ ] **不要**在排查完成前就改用 ComputerUse 替代

## 经验 2：shadow 表达式「bug」实为误诊——JSX 数组拼接假错误

### 反模式（误诊链条）

诊断脚本里这样写：

```javascript
// ❌ 错误：直接把多维属性值数组拼进字符串
_log.push("ctrl_pos=" + ctrlNull.property("Position").valueAtTime(2.0, false));
```

→ AE 抛出 **「Error: 数字结果无效（除以零？）」**。上一会话据此判定 `td_shadow_drama` 的表达式有 bug、渲染产物是「旧版」，**完全误诊**。

### 真实根因（三层实证）

在 JSX（ExtendScript）中，把 `valueAtTime()` 返回的**多维数组直接做字符串拼接**会触发假性「除以零」错误，即使表达式完全正常。**逐分量取值则正常**：

```javascript
// ✅ 正确：先取数组，再逐分量访问
var v = ctrlNull.property("Position").valueAtTime(2.0, false);
_log.push("ctrl_pos=[" + v[0].toFixed(3) + "," + v[1].toFixed(3) + "," + v[2].toFixed(3) + "]");
```

**证据链（temp/probe2_shadow_result.txt）：**

```
A_CTRL_POS_EXPR  comps=[1192.729,406.366,11.995] len=3   ← 带表达式，有限有效！
B_CTRL_POS_STATIC comps=[1190.400,410.400,0.000]         ← 静态基线
```

带表达式的属性求值得到**有限有效值**，且与静态值明显偏移 → 表达式工作正常。

### 决定性证据：A/B 渲染 SHA256 对比

禁用 6 个表达式属性渲染「静态基线」，恢复后再渲染「动画版」，对比产物：

| 版本 | 文件 | 大小 | SHA256 |
|------|------|------|--------|
| 动画（表达式启用） | `P3V4_td_shadow_drama_verify.mp4` | 100017 | `8E164836410461734497BCF1654CCBFF1AA94E380B5BA0AB3EDFCACB92E1DAF4` |
| 静态（表达式禁用） | `shadow_static_ab.mp4` | 100017 | `3393184D78E7D2AAFD168D4DD5B1A552C5636E79F166BB444D1E4237E3014DBF` |

> **两文件字节数相同（100017）但 SHA256 不同 → 表达式确实改变了渲染内容。**
> 仅看文件大小会误判「表达式无效」（H.264 对不同内容可能压缩出相同字节数）；**必须比 SHA256**。
> 恢复表达式后 `ctrl_pos t2=[1192.73,406.37,11.99]`（temp/shadow_ab_result.txt: RESTORED:6/6），状态完好。

### ✅ 检查清单（表达式诊断）

- [ ] 诊断脚本中**禁止**把 `valueAtTime()`/数组属性直接拼进字符串，必须逐分量 `v[0]/v[1]/v[2]`
- [ ] 判断「表达式是否生效」的唯一黄金标准 = **A/B 渲染对比 SHA256**，不是文件大小、不是 `expressionError` 字段
- [ ] A/B 测试用 `try/finally` 确保表达式**必定恢复**（`saved[d].p.expression=""` 禁用 → finally 恢复）
- [ ] 看到「数字结果无效（除以零？）」先怀疑**自己的诊断脚本**，而非被测表达式
- [ ] `expressionError` 为空 + 求值报假错误 → 高度提示是拼接假错误

## 经验 3：Bridge 文件协议要点——状态机、去重、字段差异

### 协议状态机（现场实证，`.ae-mcp-bridge/`）

**命令文件 `ae_command.json`（写入侧）：**
```json
{"command":"runScript","args":{"file":"C:/abs/path/script.jsx"},"timestamp":"20260729135820385","processed":false}
```
- `processed:false` → bridge 消费后改写为 `processed:true`（**processed 状态机**，headless 版）。
- 开源 panel 版用 `"status":"pending"` 触发，二者**不兼容**，严禁同时部署两套。

**结果文件 `ae_result.json`（读取侧）：**
```json
{"command":"runScript","status":"success","result":{"success":true,"data":{"result":"<脚本返回的JSON字符串>"}}, "timestamp":"2026-07-29T13:58:50"}
```
- 脚本返回值落在 **`result.data.result`**（字符串，需二次 `JSON.parse`）。
- **`timestamp` 是 AE 侧 ISO 格式，不回显命令时间戳** → 轮询匹配**不能**用命令 ts 做子串匹配（本会话 `send_jsx.ps1` 即因此假超时，修复为按 `command` 字段 + 新 mtime 匹配）。

### 去重机制

- bridge 用 `timestamp + "_" + command` 去重。**每条命令 timestamp 必须唯一**（用 Unix 毫秒或紧凑时间串），否则会被当作重复命令丢弃。

### ⚠️ 字段差异陷阱（多 build 并存，实测）

`executeAtomScript` 命令的脚本正文字段名**因 bridge 实现而异**：

| Bridge 实现 | 文件 | 脚本字段 | 结果回传 |
|-------------|------|----------|----------|
| 根目录 headless 监听器 | `ae_mcp_auto_listener.jsx` (L1294) | **`args.script`** | `executeScript()` 返回值 |
| MCP 扩展版 | `mcp-extension/scripts/executeAtomScript.jsx` (L43) | **`args.scriptContent`** | eval + 签名校验 + dryRun + 安全校验 |
| 增量脚本约定 | `ae_additive_scripts/*.jsx` | — | **`$.global.__aeAdditiveResult`**（全局通道） |

> **陷阱**：若 MCP 服务器发送 `scriptContent` 但激活的监听器只认 `script`（或反之），命令会「成功消费但脚本为空」→ 静默失败。这正是经验 1「build 指向错误目录」的连带后果。**发命令前必须确认激活 bridge 的字段约定。**

### ✅ 检查清单（发送 bridge 命令）

- [ ] 命令文件含 `command` / `args` / 唯一 `timestamp` / `processed:false`
- [ ] 确认激活 bridge 的脚本字段名（`script` vs `scriptContent` vs `file`/`code`）
- [ ] 轮询结果按 `command` 字段 + 文件新 mtime 匹配，**不要**用命令 ts 子串匹配
- [ ] 从 `result.data.result` 取脚本返回，必要时二次 `JSON.parse`
- [ ] 写命令文件用 `[System.IO.File]::WriteAllText(..., UTF8)` 避免 BOM
- [ ] 同一会话只部署一套 bridge 协议

## 经验 4：自动化脚本禁用 alert()——会阻塞整条管线

### 反模式

```javascript
// ❌ 旧文档（AE-Bridge避坑指南.md 2.4）甚至推荐这样做：
alert("Done: " + results.status);   // 经 bridge eval 执行时弹出模态对话框
```

→ 经 bridge 的 `eval`/`runScript` 执行时，`alert()` 弹出**模态对话框**，阻塞 `scheduleTask` 轮询，**整条自动化管线卡死**，后续所有命令无法消费。

### 正确做法

1. **删除一切 `alert()`**。
2. 结果回传双通道：
   - **eval 返回值**：脚本以 IIFE 包装，`return` 结果对象/字符串 → 落在 `result.data.result`。
   - **`$.global.__aeAdditiveResult`**：增量脚本把 JSON 报告写入该全局变量（`ae_additive_scripts/` 约定）。
   - **结果文件落盘**：同时写 `temp/xxx_result.txt`（双保险，便于离线核对）。

```javascript
// ✅ 正确模板（IIFE + try/catch + 双通道回传，无 alert）
(function () {
    var report = { status: "success", steps: [] };
    try {
        // ... 业务逻辑 ...
    } catch (e) {
        report.status = "error";
        report.error = e.toString() + " (line " + e.line + ")";
    }
    // 通道A：结果文件落盘
    var f = new File("C:/.../temp/xxx_result.txt");
    f.encoding = "UTF-8"; f.open("w"); f.write(report.steps.join("\n")); f.close();
    // 通道B：全局结果通道
    $.global.__aeAdditiveResult = JSON.stringify(report);
    return JSON.stringify(report);   // 通道C：eval 返回值
})();
```

### ✅ 检查清单（编写自动化 JSX）

- [ ] 全脚本**无任何 `alert()` / `confirm()` / `prompt()`**
- [ ] IIFE 包装 + `try/catch`，错误写入 report 而非抛出阻塞
- [ ] 结果三通道：eval return + `$.global.__aeAdditiveResult` + 结果文件落盘
- [ ] 渲染/长任务脚本写 `PASS/FAIL` 标记 + `OVERALL:PASS:x/y` 汇总行，便于机器判读

## 经验 5：PowerShell 5.1 以 GBK 读取无 BOM 的 UTF-8 → 中文乱码

### 反模式

- PowerShell 5.1 默认按系统 ANSI（中文 Windows = GBK/CP936）读取**无 BOM 的 UTF-8** 脚本与控制台输出。
- 后果：
  - `.ps1` 脚本含中文字面量 → 解析报错（本会话 `verify_state.ps1` 首版即因此失败）。
  - `Get-ChildItem` 列中文目录名 → 控制台显示乱码（如 `00-ÿռ¼`）。
  - 按中文**文件名**做 `Test-Path` / 匹配 → 因乱码恒为 false。

### 正确做法

1. **脚本文件**：避免在 `.ps1` 中嵌入中文字面量；用 ASCII 通配符（如 `Get-ChildItem -Filter '04-*'`）枚举中文目录。
2. **写出**：用 `[System.IO.File]::WriteAllText($path, $text, [System.Text.Encoding]::UTF8)`（带 BOM，PS 5.1 可正确回读）。
3. **匹配策略**：用 **`Select-String` 按文件内容匹配**，而非按（会乱码的）文件名匹配。
4. **读取**：`Get-Content -Encoding UTF8`；或把清单写入 UTF-8 文件再用编辑器/Read 工具读。

### ✅ 检查清单（PowerShell 处理中文）

- [ ] `.ps1` 源码不嵌入中文字面量，改用 ASCII 通配符枚举
- [ ] 写文件用 `WriteAllText(..., [System.Text.Encoding]::UTF8)`，不用裸 `>`（默认 UTF-16LE）
- [ ] 中文资源用 `Select-String` **内容匹配**，不做文件名匹配
- [ ] 读中文输出用 `Get-Content -Encoding UTF8` 或 UTF-8 文件中转

## 经验 6：模态对话框阻塞全部 scheduleTask——报错弹窗刷屏

### 反模式（错误归因）

- 现象：bridge 不再消费命令、`ae_auto_listener.log` 在某时刻后彻底静默，AE 反复弹「在行 0 无法执行脚本。After Effects错误：当模式对话框正在等待回应时，无法运行脚本。」
- **错误归因**：「bridge 又崩了」「轮询死了」「协议不可靠」→ 仓促重启 AE 或放弃 bridge。

### 真实根因（2026-07-29 实证）

AE 规定模态对话框等待响应期间禁止执行脚本。所有 `app.scheduleTask` 回调（bridge 500ms 轮询、面板自动打开任务）触发即被拒绝，且每次拒绝弹一个报错框。**报错框本身也是 modal**→只要底层 modal 不关，报错以约 500ms 频率反复出现（刷屏）。

底层 modal 常见来源：①崩溃恢复提示（AE 崩溃后重启必弹）；②缺失字体/效果警告；③「是否保存更改？」（切项目时有未保存修改）；④项目冲突（多进程同时 openProject）。

**识别特征**：bridge 日志某时间戳后再无新条目（轮询与面板任务全静默）；AE 进程仍在；MainWindowTitle 可能仍显示项目名。

### 正确做法

1. **关闭底层那个 modal（不是报错框！）**——它可能压在报错框下面或藏在任务栏；「是否保存」一律点「否」。
2. 关闭后 scheduleTask **自动恢复**，无需重启 AE；立即 ping 验证。
3. 人不在现场时用 ComputerUse 桌面自动化代点。
4. 若 AE 已崩溃（进程消失），按启动 SOP 重启。

### ✅ 检查清单（bridge 无响应·报错刷屏）

- [ ] 先查 AE 进程是否存在（消失=崩溃，按 SOP 重启）
- [ ] 查日志：某时刻后无新条目→大概率 modal 阻塞
- [ ] 找到并关闭**底层** modal（非报错框），「是否保存」选「否」
- [ ] 关闭后 ping 验证恢复，无需重启
- [ ] **不要**仓促重启 AE 或判定「协议不可靠」

## 经验 7：$.evalFile 自动打开面板的两个致命陷阱

### 反模式（2026-07-29 实证的问题实现）

```javascript
// ❌ 陷阱①：传 File 对象给 evalFile；陷阱②：先置成功标志
var panelFile = new File("C:/Program Files/.../mcp-bridge-auto.jsx");
$.global.__mcpPanelOpened = true;   // 在成功之前就置位
$.evalFile(panelFile);              // 抛 TypeError: 无法转换为 /c/Program%20Files/...
```

### 真实根因

| # | 陷阱 | 机理 |
|---|------|------|
| ① | `$.evalFile(File对象)` 抛 `TypeError: 无法转换为 /c/Program%20Files/...` | ExtendScript 对 File 对象路径做 URI 编码（空格→%20）后无法还原为可执行路径 |
| ② | 成功标志设在 evalFile 之前 | evalFile 抛异常时标志已置位，幂等逻辑误判「已成功」→永不重试；**日志看似正常实则面板从未打开**，极具迷惑性 |

### 正确做法

```javascript
// ✅ 传字符串路径 + 成功后才置标志
var panelPath = "C:/Program Files/.../mcp-bridge-auto.jsx";
if (new File(panelPath).exists) {
    $.evalFile(panelPath);              // 字符串路径
    $.global.__mcpPanelOpened = true;   // 仅成功后置位
}
```

### 验证要点

修改启动/bridge 脚本后**必须重启 AE**才生效（运行中的 bridge 加载的是旧代码）；重启后查 `ae_auto_listener.log` 应出现 **"MCP panel auto-opened"**；若只见 "task scheduled" 或出现 "WARN: MCP panel open failed" 则说明未真正打开。

### ✅ 检查清单（自动加载面板/脚本）

- [ ] `$.evalFile` 一律传**字符串路径**，不传 File 对象
- [ ] 成功标志**仅在加载成功后**设置，失败保留重试机会
- [ ] 修改后重启 AE 验证，以日志 "auto-opened" 为准（不信 "scheduled"）

## 经验 8：多 MCP 进程争写 ae_command.json——命令互相覆盖

### 反模式

以为「环境里只有我自己的 bridge」，直接写命令等结果→命令被神秘冲掉、结果被覆盖、项目被切到别的项目。

### 真实根因（2026-07-29 实证）

系统同时运行多个 AE 相关进程，其中多个**共享同一个 `.ae-mcp-bridge/ae_command.json`**：

| 进程 | 识别 | 行为 |
|------|------|------|
| 无头 bridge `2_mcp_bridge_loader.jsx` | 自动化主力（Startup 自动加载） | 轮询 ae_command.json，写 ae_result.json 格式 `{command,status,result,timestamp}` |
| `node after-effects-mcp-main/build/index.js` | 开源 MCP 服务器 | 读写同一文件，自行下发 ping/openProject/runScript，写 `{"status":"idle","result":null}` |
| `python ae_tools_mcp_server.py` | 项目自带 MCP | 同样读写该文件 |
| `mcp-bridge-auto.jsx` 面板 | ScriptUI 面板 | 走独立路径 `Documents/ae-mcp-bridge/`（**无冲突**，安全） |

**结果文件格式辨来源**：`{"status":"idle","result":null}` = 看门狗/MCP服务器；`{command,...,timestamp}` = 我的无头 bridge。

### 正确做法

1. 发命令前 `Get-Process python,node` 确认干扰源；
2. 发命令后**尽快读结果**（bridge 500ms 轮询，抢在看门狗覆盖窗口前）；
3. 干扰严重时 `Stop-Process` 掉 after-effects-mcp 的 node 进程；
4. 发命令前清空残留 ae_command.json（置 processed:true）防毒杀；
5. 启动后检查 MainWindowTitle 确认是目标项目（防被看门狗 openProject 切走）。

### ✅ 检查清单（多进程环境）
