## 一句话总纲

> **aerender 命令行渲染本身是可靠的，前提是正确应对中文 AE 的模板名差异、子进程编码、输出扩展名自动检测三大问题。**
> 此前渲染失败的核心原因是：中文 AE 的模板名（"最佳设置"/"无损"等）与英文模板名（"Best Settings"/"Lossless"）不匹配，且 fallback 策略遍历笛卡尔积导致启动次数爆炸、超时失败。

## 经验 1：中文 AE 模板名不匹配——aerender 冷启动就失败

### 反模式（错误路径）

```python
# ❌ 错误：只准备了英文模板名，以为 aerender 能自动识别
OM_TEMPLATES = {
    "mov": ["Lossless", "Apple ProRes 422 HQ", "Animation"],
    "h264": ["H.264 - Match Source - High bitrate", "H.264"],
}
RS_TEMPLATES = {
    "best": ["Best Settings", "Best", "Multi-Machine Settings"],
}
```

→ 中文 AE 渲染队列中**不存在**这些英文模板名 → aerender 报 `No render settings template was found with the given name` → 退出码 0 但无输出文件 → 被误判为 CANNOT_WRITE_OUTPUT。

### 真实根因（已实证）

| # | 根因 | 证据 / 机理 |
|---|------|-------------|
| 1 | **中文 AE 的模板名是中文**，与英文 AE 完全不同的字符串 | 手动测试：aerender 不传 `-OMtemplate`/`-RStemplate` 参数时使用默认设置（H.264 - 匹配源 - 高比特率），**立即渲染成功**（47KB MP4, 15 秒） |
| 2 | 模板错误时 aerender 返回退出码 0 而非非零值 | 实测：`No render settings template was found` 场景下返回码 0，但无输出文件；引擎此前误判为「写入成功但没有文件」 |
| 3 | 笛卡尔积遍历模板组合 × 多次重试 → 启动次数爆炸 | 每次 aerender 冷启动 15-20 秒，如果模板组合 10+ 个（如 OM×RS=8×5=40 组），总耗时可能超过 10 分钟 |

### 正确做法

1. **把 `None`（不传模板参数）作为第一候选**——不传模板 = 使用渲染队列默认设置，**任何语言版本的 AE 都 100% 成功**。
2. 为每个格式准备**英文 + 中文**双列表，英文版优先。
3. 采用**线性 fallback 策略**而非笛卡尔积：先 (None,None) → 固定命名 OM 遍历命名 RS → 固定命名 RS 遍历剩余命名 OM。
4. 模板错误码（OM_TEMPLATE_NOT_FOUND / RS_TEMPLATE_NOT_FOUND）**不能被 returncode==0 覆盖**。

### 决定性证据：手动测试

```powershell
# 不传任何模板参数 → 15 秒渲染成功
& aerender -project test.aep -comp RenderTest_v2 -output test.mov -v ERRORS_AND_PROGRESS
# 输出: test.mp4 (47KB, H.264 默认), exit code 0
```

### ✅ 检查清单（aerender 模板配置）

- [ ] OM_TEMPLATES 和 RS_TEMPLATES 必须包含中文模板名（"无损"/"最佳设置"/"H.264 - 匹配源 - 高比特率"）
- [ ] 每个格式的候选列表**以 `None` 开头**（不传参数 = 默认设置，最可靠）
- [ ] fallback 使用线性策略（非笛卡尔积），限制模板尝试次数
- [ ] 模板错误码优先于 returncode 判断（aerender 返回 0 不代表成功）

## 经验 2：aerender 返回 0 但无输出文件——错误码误判

### 反模式

```python
# ❌ 错误：returncode==0 但无输出文件 → 一律判为 CANNOT_WRITE_OUTPUT
if returncode == 0 and not output_p.exists():
    detected_code = CANNOT_WRITE_OUTPUT
```

→ 模板错误、合成不存在、项目打开失败等场景下 aerender 都可能返回 0 但不写文件 → 被误判为「写入失败」，丧失重试和模板切换的机会。

### 正确做法

```python
# ✅ 正确：先从日志解析具体错误码，仅当无更具体错误时才判为写入失败
detected_code = parse_from_log(...)  # 优先从日志解析
specific_errors = {OM_TEMPLATE_NOT_FOUND, RS_TEMPLATE_NOT_FOUND, COMP_NOT_FOUND, ...}
if returncode == 0 and not output_p.exists() and detected_code not in specific_errors:
    detected_code = CANNOT_WRITE_OUTPUT  # 仅兜底时判为写入失败
```

### ✅ 检查清单（错误码解析）

- [ ] 错误码解析**优先从日志文本**检测（`parse_aerender_error()`），而非仅依赖 returncode
- [ ] returncode==0 但无输出文件时，先检查是否匹配模板/项目错误
- [ ] 每个错误码附加 `retryable` 和 `category` 属性，便于重试策略决策

## 经验 3：Windows 中文环境——子进程编码与日志编码

### 反模式

```python
# ❌ 错误：硬编码 UTF-8 读取 aerender 日志
content = log_file.read_text(encoding="utf-8")
job.process = subprocess.Popen(cmd, encoding="utf-8", ...)
```

→ 中文 Windows 命令行默认编码为 GBK/CP936，aerender 输出的日志也是 GBK 编码 → `read_text(encoding="utf-8")` 读取汉字百分比字符 → 进度解析失败、日志显示乱码。

### 正确做法

```python
# ✅ 正确：使用 locale.getpreferredencoding() 自动适配系统编码
import locale
sys_enc = locale.getpreferredencoding(False)  # Windows 中文 = "cp936"

# 子进程：使用系统编码
job.process = subprocess.Popen(cmd, encoding=sys_enc, ...)

# 日志读取：多编码自动探测
for enc in (sys_enc, "utf-8", "gbk", "cp936"):
    try:
        content = log_file.read_text(encoding=enc, errors="strict")
        break
    except UnicodeDecodeError:
        continue
```

### ✅ 检查清单（Windows 编码）

- [ ] subprocess 使用 `locale.getpreferredencoding(False)` 而非硬编码 `"utf-8"`
- [ ] 日志文件读取使用多编码自动探测（gbk → utf-8 → cp936）
- [ ] 进度正则同时支持中文、英文、日文 AE 日志格式

## 经验 4：输出扩展名自动变化——预期 .mov 实际 .mp4

### 反模式

```python
# ❌ 错误：只检查 user 指定的输出路径
output_p = Path(job.output_path)  # 假设是 render.mov
if returncode == 0 and output_p.exists() and output_p.stat().st_size > 1024:
    return True
```

→ 测试发现：不传 `-OMtemplate` 时，中文 AE 默认使用 **H.264** 输出模块 → 输出文件是 `render.mp4` 而非 `render.mov` → 引擎一直检查 `render.mov` 是否存在 → 永远找不到文件 → 判定失败。

### 正确做法

```python
# ✅ 正确：搜索同目录下同名不同扩展名的媒体文件
def _find_actual_output(p: Path) -> Path:
    if p.exists() and p.stat().st_size > 0:
        return p
    stem = p.stem; parent = p.parent
    if parent.exists():
        candidates = list(parent.glob(f"{stem}.*"))
        media_exts = {".mp4", ".mov", ".avi", ".png", ".tiff", ".exr"}
        for c in sorted(candidates, key=lambda x: x.stat().st_mtime, reverse=True):
            if c.suffix.lower() in media_exts and c.stat().st_size > 1024:
                return c
    return p

# 找到实际文件后更新 job.output_path
job.output_path = str(actual_output)
```

### ✅ 检查清单（输出文件检测）

- [ ] 额外搜索同目录下同名不同扩展名的媒体文件
- [ ] 找到实际输出后更新 `job.output_path`
- [ ] 等待文件写入时使用 `_find_actual_output()` 重新检测

## 经验 5：进度正则不支持中文时间码格式

### 反模式

```python
# ❌ 错误：只支持英文进度格式
PROGRESS_PATTERNS = [
    re.compile(r"Rendering:\s+\S+\s+/\s+\S+\s*\((\d+)/(\d+)\)"),
    re.compile(r"Rendering frame\s+(\d+)\s+of\s+(\d+)"),
]
```

→ 中文 AE 日志格式为 `0:00:00:00 (1): 0 秒`（时间码 + 帧号 + 中文描述），没有任何 pattern 匹配 → 进度始终为 0%。

### 正确做法

```python
# ✅ 正确：增加中文时间码格式
PROGRESS_PATTERNS = [
    re.compile(r"\d+:\d+:\d+:\d+\s*\((\d+)\)[^0-9]*(\d+)?"),  # 中文时间码
    re.compile(r"\d{2}:\d{2}:\d{2}:\d{2}\s*\((\d+)\)"),       # 英文时间码
    re.compile(r"\((\d+)\s*/\s*(\d+)\)"),                       # 通用 (1/72)
    # ... 中文、英文、日文等
]
```

### ✅ 检查清单（进度解析）

- [ ] 进度正则覆盖中文时间码格式 `0:00:00:00 (N)`
- [ ] 测试四种语言格式：英文、中文、中文时间码、日文
- [ ] 日志文件优先使用文件系统编码读取（见经验 3）

## 经验 6：进程管理与 AE 残留进程

### 反模式

```python
# ❌ 错误：aerender 退出后不清理残留进程
job.process = None  # 只清理了 Python 侧引用，没清理 AE 进程
```

→ aerender 每次冷启动创建一个新的 AfterFX 实例。如果渲染失败或超时，AE 进程可能残留 → 下次启动时 `-reuse` 自动检测到已有 AE 实例 → 尝试复用 → 但残留实例可能处于错误状态 → 渲染失败。

### 正确做法

```python
# ✅ 正确：递归终止进程树
def _terminate_process_tree(proc):
    """终止进程及其所有子进程"""
    try:
        if platform.system() == "Windows":
            subprocess.run(
                ["taskkill", "/F", "/T", "/PID", str(proc.pid)],
                capture_output=True, timeout=5
            )
        else:
            proc.terminate()
            proc.wait(timeout=5)
    except Exception:
        try: proc.kill()
        except: pass
```

### ✅ 检查清单（进程管理）

- [ ] 渲染结束/失败/超时后**必须**终止进程树（含 aerender 和 -mp 子进程）
- [ ] 启动前检测 `Get-Process AfterFX` 确认无残留
- [ ] 强杀后等 3-5 秒再启动（操作系统释放进程锁）

## 经验 7：aerender 与 AfterFX -r 的路径关系

### 关键发现

- `detect_aerender()` 返回路径 → `Path(path).parent / "AfterFX.exe"` 即可定位 AfterFX

## 对既有文档的纠正

| 旧结论 | 纠正（本次实证） |
|--------|----------------|
| 「aerender 不指定模板失败时可以靠多次重试」 | **不指定模板（None）才是最快路径**，测试证明 15 秒冷启动即成功，不应先尝试命名模板 |
| 「aerender 返回 0 就是成功」 | **aerender 返回 0 但可能没有输出文件**（模板错误/合成不存在），必须结合日志分析和文件存在性判断 |
| 「输出扩展名按用户指定」 | **输出扩展名由 OM 模板决定**，H.264 默认输出 .mp4 而非 .mov，必须自动检测 |
| 「UTF-8 编码可以覆盖所有场景」 | **中文 Windows 下 aerender 日志是 GBK 编码**，必须使用系统编码自动探测 |
