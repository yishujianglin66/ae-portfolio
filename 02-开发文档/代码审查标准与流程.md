## 0. 审查结论摘要 (Executive Summary)

我用三路并行代码审计 + 需求/架构文档通读的方式扫描了整个仓库，结论先说：

**你比自己以为的走得更远。** 仓库已不是"没有审查机制"的状态，而是已经具备一套相当成熟的自动化质量门禁（见 §1.1）。真正的问题不是"缺机制"，而是：

1. **机制不统一、不闭环** —— 有 flake8、有 pytest、有秘密扫描、有 JSX 语法门，但**覆盖率门禁只在 `pyproject.toml` 里声明、从未在 CI 真正跑过**；flake8 **只扫了 7 个硬编码文件**，新代码大量漏网。
2. **缺"人审"这一层** —— 所有自动化都是机器门禁，但**没有落地的 PR 人工审查流程、 reviewer 角色、严重级定义、SLA**。这正是你问的"审查流程"的核心缺口。
3. **编码规范只覆盖旧栈** —— `编码规范.md` 只写了 ExtendScript/CEP（JS/JSX），**主流语言 Python 没有任何书面标准**，尽管它是当前 5885 行单体管线的载体。
4. **路线图已过时** —— `开发路线图` 里写的"无统一测试框架"是 2026-07-23 的状态；现状已有 pytest + coverage + CI，该条技术债已清偿，需更新以免误导。

> 一句话：自动化底子很好，缺的是**把已有工具串成闭环 + 补上人的审查流程 + 补一份 Python 标准**。下面给出标准、流程、落地计划三件套。

## 1. 项目现状诊断：既有机制 vs 真实缺口

### 1.1 已有机制（很强，不要重复造轮子）✅

| 机制 | 位置 | 状态 | 备注 |
|------|------|------|------|
| pytest 套件 | `tests/` + `puppet-automation/tests/` | ✅ 存在 | marker 隔离做得好：`real_ae`/`real_ffmpeg`/`silhouette` 等 |
| 覆盖率配置 | `pyproject.toml:156-197` `fail_under=60` | ⚠️ **声明但 CI 未跑** | CI 里 pytest 不带 `--cov` |
| flake8 门禁 | `ci.yml:91-95` | ✅ 阻断合并 | 但 `extend-ignore` 过宽，且**只扫 7 个文件** |
| 秘密正则扫描 | `ci.yml:97-139` | ✅ 阻断 | 覆盖 password/api_key/private key/openai/modelscope |
| JSX 语法门 | `ci.yml:13-24` `check_jsx_syntax.py` | ✅ 阻断 | 防 D-24 类事故（未加引号路径数组）重演 |
| 前端 TS 门 | `ci.yml:141-177` `tsc --noEmit` + build | ✅ | ae-dashboard |
| 编译器门 | `ci.yml:179-216` | ✅ | compiler/ TS 构建 + 真实执行 |
| Docker 门 | `ci.yml:217-238` | ✅ | 镜像构建 + compose 校验 |
| **产出物**质量门 | `quality-gate.yml` | ✅ | 注意：这是**视频产物**质量，非代码质量 |
| 敏感文件 gitignore | `.gitignore` | ✅ 很完善 | `.env`/`.mcp_secret`/`cookies/`/bridge 目录/模型权重全覆盖 |

**结论**：秘密泄漏的"仓库侧"风险已被 `.gitignore` + 正则扫描双重兜底；JS 侧有专门规范；CI 骨架完整。**不要推翻重来，要在其上加层。**

### 1.2 真实缺口（查漏补缺）🔍

按严重度排列（本专家框架：🔴 阻断 / 🟡 建议 / 💭 优化）：

#### 🔴 阻断级（必须在建立流程时先堵住）

- **G1 · 覆盖率门禁从未在 CI 执行**
  `pyproject.toml` 配了 `fail_under=60`，但 `ci.yml` 的所有 `pytest` 调用都**没有 `--cov`**。覆盖率配置是装饰性的。最危险的是 `ae/ae_agent_pipeline.py`（**5885 行单体**）几乎没有单测保护，而它是管线主干。
  → 必须在 CI 加 `pytest --cov --cov-fail-under=60`（先 60，逐步提）。

- **G2 · flake8 只扫了 7 个硬编码文件，且忽略项过宽**
  `ci.yml:94` 只扫 `web/api_server.py web/auth_system.py web/integrator_api.py database.py core/health_checker.py core/quality_gate.py`。
  而 `ae/`（91 个 .py）、`13-素材获取与搜索/`、`14-Silhouette知识库/`、`analysis/`、`integrations/` 等**完全未被 lint**。
  同时 `extend-ignore` 含 `F401`(未用导入) `F841`(赋值未用) `E402`(导入不在顶部) —— 这些都是实打实的坏味道却被放行。
  → 把 lint 范围扩展到全部一方 Python 包，收紧 ignore（至少开 F401/F841）。

- **G3 · pytest 在 CI 跑"精选文件列表"，新测试不进 CI**
  `ci.yml:69,77,83` 用硬编码的文件名调用 pytest。新增到 `tests/` 但不在列表里的测试**永远不会被 CI 执行**，形成"有测试但没跑"的假安全感。
  → 改为跑整个 `tests/`（用 `addopts` 里的 marker 排除真实环境测试）。

#### 🟡 建议级（本迭代内解决）

- **G4 · Python 无书面编码规范**
  `编码规范.md` 只覆盖 ExtendScript/CEP。**主流的 Python 代码没有任何风格/类型/错误/日志约定**。
  → 新增 §3.7「Python 专属审查规则」，并纳入本文件。

- **G5 · 两套以上管线并存，无收敛决策**
  `ae/ae_agent_pipeline.py`（单体）+ `puppet-automation/`（19 引擎，被 MOC 定为"当前主线"）+ `UnifiedPipeline v2`（quality-gate 引用）。路线图技术债 #5 已记录但未决。
  → 审查流程需强制：新增管线能力前先声明归属，避免第 N 套并存。

- **G6 · `ae/` 四份 process_manager 高度重复**
  `ae_process_manager.py` / `pr` / `ps` / `au` 各含 ~16 个同名方法（`__init__`/`setup_logging`/`find_windows`/`send_wm_close`/`detect_memory_leak`…），约 30+ 重复方法 + 多处 `except Exception: pass`。
  → 抽 `BaseProcessManager`；review 时把"复制粘贴式新增"列为 🟡。

- **G7 · 裸 `except:` 吞掉一切（含 KeyboardInterrupt）**
  `ae/ae_agent_pipeline.py:289` 用裸 `except:` 静默回退默认配置。属阻断级隐患，但因其已存在于主干，列为"建议优先修"。
  → 改为 `except (OSError, json.JSONDecodeError)` 并 log。

- **G8 · `print` vs `logging` 不一致**
  `13-素材获取与搜索/` 大量 `print()`；`benchmark.py` 39 处 print 0 处 logging；核心模块已用 logging。
  → 审查规则：库代码禁止裸 `print`（CLI 入口除外）。

- **G9 · 硬编码绝对路径（exe 探测 + 素材默认位置）**
  `ae/*_process_manager.py:123-125` 写死多盘符 exe 候选；`14-` 模板用 `D:/footage`、`D:/output`；`13-` 用 `D:/AE-Work/cookies`。
  → 审查规则：路径必须从 `core.config` 或环境变量推导，禁止提交含用户名/盘符的绝对路径（与 `编码规范.md` §5 对齐，扩展到 Python）。

- **G10 · 依赖漏洞无扫描**
  秘密扫描是"源码内密钥"正则，但**没有 `pip-audit`/`safety` 跑依赖 CVE**，`requirements*.txt` 的传递依赖无监控。
  → 在 CI 加 `pip-audit`。

#### 💭 优化级（技术债清理）

- **G11 · `05-测试套件/` 名不副实**
  该目录是**手工 AE ExtendScript/JSX 验证夹具**（17 .jsx + 11 .js + 报告），无法在 CI/headless 跑，与 91 个 `ae/*.py` 毫无 import 关系。真正的 Python 测试在根 `tests/`。
  → 归档到 `archive/`，避免与 pytest 体系混淆（已有文档自注"历史文档"）。

- **G12 · 安全扫描是纯正则**
  无法识别 `shell=True`、危险的 `subprocess` 拼接、`.json` 内嵌 token（虽 `.json` 未被 skip，但仅匹配固定模式）。可引入 `bandit`。

- **G13 · 无 pre-commit 本地门禁**
  `dev` 依赖含 `pre-commit` 但未见 `.pre-commit-config.yaml` 落地。本地 push 前无拦截。

## 2. 审查范围与分层 (Scope)

| 纳入审查（一方代码） | 排除（理由） |
|----------------------|--------------|
| `ae/`、`core/`、`config/`、`bridges/`、`effects/`、`media/`、`models/`、`audio/`、`analysis/`、`learning/`、`integrations/`、`knowledge_base/`、`compiler/`、`web/`、`ai/`、`puppet-automation/` | `external/`、`AE-Scripts/`（`.gitignore` 已标记为第三方，不纳入版本控制，仅当**直接调用**时才审接口） |
| `13-素材获取与搜索/`、`14-Silhouette知识库/`（.py） | `*.pyc`、`__pycache__/`、`venv/` |
| `cep_panel/`、`mcp-extension/`（JS/JSX） | 知识库文档（`10-`~`15-` 的 .md 内容，非代码） |
| 根级 `*.py` 模块（`logger.py`/`exceptions.py`/`config_schema.py` 等） | 媒体/模型/输出产物 |

**分层原则**：
- **L1 核心主干**（`ae/ae_agent_pipeline.py`、`core/*`、`puppet-automation/engines`）：🔴 阻断项零容忍，覆盖率优先。
- **L2 工具/集成**（`13-`/`14-`、各 `*_client.py`、downloader）：重点审安全（密钥/网络）与错误处理。
- **L3 实验/脚本**（`dev_scripts/`、`examples_*.py`、`analysis_out/`）：放宽，但禁止提交密钥与绝对路径。

## 3. 代码审查标准 (The Standard)

采用本专家统一严重级：**🔴 阻断（不得合并）/ 🟡 建议（需附说明或修）/ 💭 优化（可选）**。
合并规则：**任何 🔴 未清零 = 禁止合并**；🟡 可由 reviewer 与作者协商后 waiver，但需记录理由。

### 3.1 五维审查清单（每次 PR 必过）

| 维度 | 必查项 | 本项目高频雷区 |
|------|--------|----------------|
| **正确性** | 错误处理、边界、返回值、并发 | 裸 `except`(G7)、`except: pass` 静默吞错、单体耦合 |
| **安全** | 密钥、注入、路径、依赖 | 硬编码路径(G9)、downloader 无速率限制、缺 `pip-audit`(G10) |
| **可维护性** | 单一职责、重复、命名、日志 | 5885 行单体(G1)、4 份 process_manager 重复(G6)、print(G8) |
| **性能** | N+1、阻塞、内存、I/O | AE 内同步长操作（旧栈已规范）、大文件一次性读入 |
| **测试** | 关键路径有测试、可运行 | 覆盖率未强制(G1)、CI 精选文件(G3)、`05-测试套件` 误导(G11) |

### 3.2 安全规则（本项目细化）

🔴 **以下任一情况直接打回：**
- 提交真实密钥/会话凭证（`.env` 之外硬编码 `sk-`、`ms-`、`sessionid`、`ttwid` 等）。注：仓库侧已被 `.gitignore`+正则扫描兜底，但**本地 `cookies/` 等活凭证仍存在于工作树**，属运维风险，不在代码审查范围但应告警。
- 使用 `shell=True` 或字符串拼接进 `subprocess`/`os.system`。现状良好（均为列表参数），review 时守住这条线。
- `eval()`/`exec()` 处理不可信输入（JS 旧栈的 `json2.js` 已解决，Python 侧禁止）。

🟡 **建议：**
- 网络下载器（`13-` 的 douyin/bilibili/youtube downloader）增加请求间隔/速率限制与 ToS 提示。
- 失败路径显式 `raise`，不要返回 `None` 让下游静默继续。
- 加入 `bandit` + `pip-audit` 到 CI（G10/G12）。

### 3.3 正确性规则

🔴 **打回：**
- 裸 `except:`（捕获 `KeyboardInterrupt`/`SystemExit`）。→ 改用具体异常类型 + log（G7）。
- 关键路径（管线编排、引擎调度、桥接）**完全无错误返回/异常上抛**，失败时静默成功。

🟡 **建议：**
- `except Exception: pass` 至少记 `logger.warning`，保留可观测性（多处 process_manager / ai_scene_detector）。
- 跨进程通信（Python↔ExtendScript）严格走既定协议（`OK:/ERROR:/PROGRESS:`），新增通道需 review。

### 3.4 可维护性规则

🔴 **打回（仅对 L1 主干）：**
- 单文件 > 800 行且无可拆分说明（当前 `ae_agent_pipeline.py` 5885 行为例外存量，新代码不得新增此类）。

🟡 **建议：**
- 复制粘贴式新增（如第 5 份 process_manager）必须先抽基类/工具函数（G6）。
- 库代码用 `logging`（统一 `loguru`/`logger.py`），CLI 入口可用 `print`（G8）。
- 死代码（如 `ae/archive/` 与根同名文件副本）及时删/归档。

💭 **优化：** 统一配置读取入口（只用 `core.config`，消除 `ae_agent_pipeline` 自带的 `get_config_cached` 双路径）。

### 3.5 性能规则

🟡 长耗时操作（>500ms）在 AE 宿主侧必须异步（旧栈 M1/M4 已规范）；Python 侧大文件/大 JSON 避免一次性读入；外部进程调用设置超时（CI 已有 `--timeout=30`，代码侧也应设）。

### 3.6 测试规则

🔴 **打回（L1 主干）：** 新增/修改核心逻辑无对应测试，且 PR 未说明豁免理由。

🟡 **建议：**
- 网络/外部依赖测试必须 mock（CI 已用 marker 隔离真实环境，保持）。
- 覆盖率纳入 CI 门禁，初始 `fail_under=60`，每季度 +10 直至 80（G1）。
- 新增测试必须能被 `pytest tests/`（整目录）收集，禁止只加进"精选列表"（G3）。

### 3.7 Python 专属规则（**当前缺失，本文件补位**）🆕

> 这是 `编码规范.md` 未覆盖的部分，作为 Python 一方的书面标准。

| 项 | 规则 |
|----|------|
| 风格 | `flake8`（`max-line-length=120`，**开启 F401/F841/E402**），逐步引入 `black`/`ruff` |
| 类型 | 新模块 `from __future__ import annotations`；公共 API 加类型注解；CI 加 `mypy --strict` 渐进 |
| 路径 | 零硬编码绝对路径；exe/工具从 `core.config` 或运行时探测（G9） |
| 日志 | 库代码用 `logging`/`loguru`；禁止裸 `print` |
| 错误 | 禁止裸 `except:`；`except` 块至少 `logger.warning`；失败显式 `raise` |
| 命名 | 函数/变量 `snake_case`，类 `PascalCase`，常量 `UPPER_CASE`（与 `编码规范.md` §6 一致） |
| 测试 | `pytest`，文件名 `test_*.py`，真实环境用 marker 隔离 |
| 依赖 | 仅经 `pyproject.toml` 声明，禁止隐式 `import` 未声明包 |

### 3.8 JS/JSX 规则（已有，引用不重写）

直接遵循 [[编码规范]] §2（ES3/ES5 限制）、§3（废弃 API 禁止）、§4（错误返回格式）、§5（零硬编码路径）。CI 的 `check_jsx_syntax.py` 已强制执行语法门。

## 4. 代码审查流程 (The Process)

### 4.1 四道门禁（Gate Model）

```
开发者本地               GitHub PR                人工审查                  合并
─────────              ─────────                ─────────                ─────
[门1] pre-commit        [门2] CI 自动门           [门3] 专家/Reviewer       [门4] 合并守卫
 flake8/secret-scan  →   jsx-syntax + pytest  →  按 §3 标准出审查意见  →   branch protection
 + 本地 pytest --cov      + coverage + mypy         🔴清零才可 approve        required checks 全绿
```

- **门1（本地，建议）**：`.pre-commit-config.yaml` 跑 flake8 + 秘密扫描（G13）。不强制但强烈建议，避免把明显问题推到 CI。
- **门2（CI，强制）**：在现有 `ci.yml` 上**扩展**——pytest 加 `--cov --cov-fail-under`（G1）、flake8 扩到全包并收紧 ignore（G2）、加 `mypy` 与 `pip-audit`（G10）、pytest 改跑整目录（G3）。
- **门3（人审，强制）**：见 §4.2–4.4。这是当前**唯一缺失的层**。
- **门4（合并守卫）**：`main`/`develop` 设 branch protection，required checks = 门2 全绿 + 至少 1 个 reviewer approve + 🔴 清零。

### 4.2 PR 审查清单（Reviewer 勾选）

每次 PR 必答：
- [ ] **意图**：PR 描述说清"改了什么、为什么"（对照 [[开发路线图-阶段A至E]] 的归属模块）
- [ ] **安全** §3.2：无密钥、无 shell 注入、无硬编码路径
- [ ] **正确性** §3.3：无裸 except、错误可观测、关键路径有错误返回
- [ ] **可维护性** §3.4：无复制粘贴新增、日志规范、无死代码
- [ ] **测试** §3.6：有测试、能被整目录收集、覆盖率不降
- [ ] **管线归属** §G5：若是新能力，声明落在哪套管线（禁止悄无声息开第 N 套）
- [ ] **Python 规范** §3.7 / **JS 规范** §3.8 达标

### 4.3 角色与 SLA

| 角色 | 职责 | SLA |
|------|------|-----|
| Author | 自检门1、写清描述、回应意见 | 24h 内回应 review 意见 |
| Reviewer（可为本 Code Reviewer 专家） | 按 §3 出意见、定严重级、清零 🔴 | 48h 内首轮 review |
| Maintainer | 最终 approve、合并守卫、技术性决策（如 G5 收敛） | 按需 |

> **小团队现实**：作者可兼任 reviewer 自审，但 🔴 必须由另一人（或本专家）确认。AI 生成代码（本项目大量）**必须**过人审，不得 self-approve。

### 4.4 严重级判定与处置

| 级别 | 含义 | 处置 |
|------|------|------|
| 🔴 阻断 | 安全漏洞/数据风险/破坏主干/无测试的核心改动 | **禁止合并**，必须修 |
| 🟡 建议 | 可维护性/健壮性/性能隐患 | 修或书面 waiver（记录理由） |
| 💭 优化 | 风格/文档/可选重构 | 鼓励，不阻塞 |

意见格式（沿用本专家规范）：
```
🔴 **安全: 硬编码 exe 路径**
```
