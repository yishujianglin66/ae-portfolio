### 2. 根因一：`_execute_task` 终态在锁外发布，回调在锁内触发

`pipeline/batch_queue.py` 原实现：

- `try` 体内（**无锁**）执行 `task.status = TaskStatus.COMPLETED`
- `finally` 中（**持锁**）才调用 `task.on_complete(task)`

探针实测到的时间线（间隔仅 0.15ms）：

```
[dbg] _execute_task ENTER  status 尚未发布
[dbg] wait RETURNED  status=COMPLETED      ← 主线程在锁内读到"已完成"
[dbg] CALLBACK FIRED  result=42            ← 1ms 后回调才执行
F     assert callback_called[0] is True
```

`wait_for_task` / `wait_all` 都在锁内读终态，因此"看到 COMPLETED 时回调必然已跑完"应当是该队列对外提供的基本契约。修复方式：把**摘除 `_running` + 发布终态 + 计数 + 触发回调**合并进同一个临界区（`self._lock` 是 `RLock`，回调内再调队列方法不会自锁）。`on_failure` 原先在锁外触发，同样缺口，一并纳入。

同时修掉自己复查时发现的隐患：`BaseException` 穿透时任务必须仍从 `_running` 摘除，否则永久占位。

### 3. 根因二：`submit_batch` 在 submit 之后才挂载回调

原实现先 `submit()` 全部任务，再回头 `t.on_complete = combined`。快于主线程的 worker 会在挂载前就跑完任务 → `remaining` 永不为 0 → 整批回调**永不触发**。附带缺陷：`def combined(task=task, ...)` 的 `task` 是上一个循环遗留的变量（默认值被调用时覆盖，未致错但有误导性）；`on_batch_complete(results)` 直接把仍在 append 的共享列表交给回调，可能拿到不完整列表。

压测对比（每轮 6 任务、max_workers=8、200 轮）：

| 实现 | 批量回调未触发 | 结果列表不完整 |
|---|---|---|
| 旧（`git HEAD:batch_queue.py`） | **196 / 200** | 0 |
| 新（本次修复） | **0 / 200** | 0 |

修复方式：回调改为在 `submit(...)` 时作为参数原子挂载；用"全部提交完成 且 全部执行完成"双条件触发；触发时传入列表快照；用户自带 `on_complete` 先执行且异常隔离，避免单个回调异常卡死批次计数。

竞态关闭压测（新实现）：`complete` 300 轮 + `failure` 300 轮 + 并发批 200 任务，**观察到终态但回调未触发 = 0 例**。

## 四、关键经验总结

1. **"0 failed"要用重复运行验证**：时序竞态用例的特征是"单跑挂、连跑可能过、全量看负载"。只跑一次全量得到的绿灯不可信——本次实测同一文件在三种运行范围下结果不同。
2. **观测不能改变被观测对象**：上一会话的哨兵只查 `builtins.__import__`，粒度太粗；且诊断脚本若真的 `import aiohttp` 就会把 sys.modules 补回去，反而掩盖问题。本次诊断严格约束为只读探测 + 包装 `PathFinder.find_spec`（记录返回 None 的调用及栈），不改 sys.modules、不碰 `__import__`。
3. **防御性 try/except 会把症状永久固化**：`except Exception: client_timeout=None` 让测试变绿的同时，把"该导入是否真的会失败"这个问题封死了。以后遇到"加了防御就绿了"的情况，必须补一条：防御分支是否有实测证据支撑，否则应定期撤除复验。
4. **并发契约要明确写出来**：`wait_for_task` 返回终态 ⇒ 回调已执行完毕。这条契约此前只在实现里隐含，两个缺陷（锁外发布终态、submit 后挂回调）都源于它没被写清。
5. **压测对比新旧实现是低成本高置信的取证手段**：`git show HEAD:<旧路径> > tmp/xxx.py` 把修复前实现取回本地，同一压测/同一用例跑两遍，196/200 vs 0/200 的对比比任何推理都有说服力。这个手法本会话用了两次（第二次直接决定了闸门设计，见第 6 条）。
6. **回归闸门必须自证能检出它要守的那个缺陷**：竞态用例第一版（60 轮串行 submit+wait）对修复前实现**全部通过**——是个永远绿的无齿闸门。原因是缺陷窗口只有微秒级，`wait_for_task` 的 100ms 轮询几乎撞不上。改成"并发 4 任务 + 回调内 sleep 让 worker 在队列锁上串行化"后，旧实现 3/3 稳定失败、新实现 3/3 稳定通过。**判据：闸门写完要做一次"反向验证"，否则等于没写。**
7. **生产代码用 `except Exception: pass` 包住用户回调，会制造测试假象**：写闸门时回调内误写了未定义的变量名，`NameError` 被队列的吞异常逻辑吃掉，表象是"每一个任务都违反契约"——看起来像生产代码有大问题，实际是测试自己崩了。回调体保持极简（只做标记），必要时在测试里另用列表记录回调异常。
