### 任务 1：崩溃问题根本原因定位与彻底解决

**问题现象**：自动操作重启 AE 时必现崩溃，弹出 Crash Repair 对话框

**根因分析**：
```
之前的假设（错误）：Startup 目录的脚本导致崩溃
实际根因（正确）：force-kill 强制杀死 AE → 工作区/面板状态文件损坏 → 重启恢复时崩溃
```

**修复方案**：
1. ✅ **WM_CLOSE 优雅关闭** — 模拟用户点击窗口 X 按钮，完全优雅退出
2. ✅ **崩溃状态自动清理** — 启动前清理注册表 AppState、CrashRpt、临时文件
3. ✅ **保存对话框检测** — 关闭前检测是否有未保存提示，避免阻塞

**验证结果**：
- 连续重启测试：✅ 成功（WM_CLOSE 方式）
- 崩溃修复对话框：✅ 不再出现
- 面板自动恢复：✅ 正常工作

### 任务 4：Bridge 统一通信协议

**文件**：[bridge_protocol.py](file:///C:/Users/Administrator/Desktop/AE-Knowledge-Vault/ae/bridge_protocol.py)  
**文档**：[bridge_protocol_spec.md](file:///C:/Users/Administrator/Desktop/AE-Knowledge-Vault/docs/bridge_protocol_spec.md)

**架构设计**：

```
双模式通信
├── 单命令模式（向后兼容）
│   └── ae_command.json + ae_result.json
└── 队列模式（生产级）
    ├── command_queue/{priority}/  优先级队列
    ├── results/                   结果存储
    └── dead_letter/               死信队列

命令结构 (BridgeCommand)
├── command_id: UUID          全局唯一标识
├── command: str              命令名
├── params: Dict              参数对象
├── timestamp: datetime       发送时间
├── ttl: int                  超时时间（默认30s）
├── priority: Priority        HIGH/NORMAL/LOW/BACKGROUND
├── idempotency_key: str      幂等键（可选）
└── signature: str            HMAC-SHA256 签名（可选）

响应结构 (BridgeResponse)
├── command_id: UUID          对应命令ID
├── status: CommandStatus     pending/processing/completed/failed/timeout
├── result: Dict              成功结果
├── error: BridgeError        错误信息
├── progress: BridgeProgress  进度（percent + message）
├── started_at / finished_at  时间戳
└── attempt: int              重试次数

错误码体系（4大类30+）
├── 1xxx 协议错误（格式/签名/版本）
├── 2xxx AE 端错误（未运行/脚本错误/权限）
├── 3xxx 业务错误（参数/资源/操作失败）
└── 4xxx 系统错误（IO/内存/意外崩溃）
```

**可靠性特性**：

| 特性 | 说明 |
|------|------|
| **HMAC 签名** | 防篡改、防伪造，常量时间比较防时序攻击 |
| **指数退避重试** | base_delay × 2^(attempt-1) + 随机抖动 |
| **幂等性保证** | 相同 idempotency_key 只执行一次，缓存 24 小时 |
| **优先级队列** | 4 级优先级 + 低优先级自动老化升级 |
| **并发控制** | max_concurrent 限制并行执行数，保护 AE |
| **三级超时** | 命令 TTL / 执行超时 / 结果过期 |
| **死信队列** | 重试耗尽的命令进入 DLQ，支持人工干预 |
| **跨进程文件锁** | 锁文件 + 原子创建，防读写竞态 |
| **内存泄漏防护** | 取消命令 TTL + 幂等缓存 FIFO 淘汰 |

**质量评分**：9.2/10（修复 P0 问题后）

## 🔑 关键经验总结

### 1. AE 崩溃的真正元凶

```
❌ 错误认知：Startup 目录的脚本导致崩溃
✅ 正确结论：force-kill 强制关闭导致状态文件损坏

教训：排查问题时要区分"相关"和"因果"。
      脚本在 Startup 目录和崩溃同时出现，不代表脚本是原因。
      真正的原因是关闭方式。
```

### 2. WM_CLOSE vs force-kill

| 关闭方式 | 原理 | 稳定性 | 速度 | 适用场景 |
|---------|------|--------|------|---------|
| **WM_CLOSE** | 发送窗口关闭消息，让 AE 优雅退出 | ⭐⭐⭐⭐⭐ | 慢（3-10s） | 正常关闭、自动化操作 |
| taskkill /F | 强制杀死进程 | ⭐ | 快（<1s） | 进程卡死、紧急情况 |
| app.quit() | 脚本调用退出 | ⭐⭐⭐⭐ | 中 | Bridge 通信可用时 |

**最佳实践**：WM_CLOSE → 超时降级 force-kill → 清理崩溃状态

### 3. 开源 vs 自研的决策

```
当自研进度 vs 开源成熟度差距 > 2 倍时，选开源。

我们的情况：
- 自研：~5 个工具，原型质量
- 开源：40+ 个工具，社区验证
- 比值：8 倍 → 选开源，在其基础上扩展

后续策略：短期用开源，中期融合，长期统一。
```
