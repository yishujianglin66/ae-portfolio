### 1.2 三波推进逻辑

```
E0 波（服务 run53 收官）——音乐理解升级 + 防灾底座
   直接抬切点质量天花板；把人工验收变成可入库数据；堵住丢失事故。
        ↓ 产出：更高质量母版 + 结构化验收数据（蒸馏原料）

   经验→规则的蒸馏引擎 + 检索/运镜/评分三大基础模型升级。

   在 E1 数据与规则基础上做能力扩展，避免半成品污染编排。
```

> 设计判断：**不先做 E2 的生成能力**。run53 验收反馈证明当前瓶颈在"剪辑决策质量"而非"素材数量"；生成镜头是素材扩充手段，规则蒸馏才是编排质量杠杆。

## 二、设计原则（四条铁律，全部映射既有证据闸门）

1. **先评测后接入（闸门 2/3 延伸）**：任何外部模型/库接入生产路径前，必须在 gold set 或参照集上跑出实测分数并落盘 `output/evidence/enhance_<item>_YYYYMMDD/`。无评测数据的能力声明 = PLAN。
2. **8GB 显存硬约束**：7B+ 模型只考虑 4bit/GGUF 路线且必须实测峰值显存落盘；"勉强能跑"级候选（HunyuanVideo、Wan2.2-14B 原生）直接排除出主线。
3. **许可证一票否决**：GPL 传染 → 仅独立进程命令行调用（如 APISR）；非商用权重（AudioLDM2/AudioGen/Q-Align 权重）→ 排除；许可待核验项 → 核验前禁入生产。每个新权重下载后 24h 内登记 `data/artifact_manifest.json`（SHA-256 + 备份路径，沿用 P0-D 政策）。
4. **接入即蒸馏**：每个 E0/E2 能力接入生产时，其调参经验必须当轮沉淀为规则（第七节 schema），禁止"先堆功能后补文档"。

**根因假设（v2 规则 R-2026-0002 的设计输入，待验证）**：

切点跟着音符事件走 → 每个切点都"在某声音上"，但脱离了 BPM 网格相位 → 人耳判为"不在点上"。

16 分音符格）——事件选择 × 网格相位结合，而非事件时间本身。另：run56 精修版音轨 peak 1.0
削波（limiter 需留 headroom）、尾部 4 秒未渲染（aerender 627 帧收尾），两小项随 v2 一并处理。

**计划层诊断**：锚点臂 96% 切点落在 kick|snare ±80ms（中位偏差 **28ms**，>200ms 仅 1 个）；对照臂 61%（中位 56ms）。kick 中位偏差 37ms vs 79ms。切点数下降符合《鼓类型切点锚定》研究文档"kick+强拍锚定、排除 hihat"的方向——省掉的切点本来就不在鼓点上。

**附带发现已修复（2026-09-05 晚）**：分层分类器对长素材单次分配 12.21GiB 显存的根因=VLM 专家抽帧不缩放（4K 原帧进 Qwen 处理器 → 视觉 token 网格爆炸）。修复=`vlm_expert_3class.extract_frames` 统一限边 512px。实测：4K 源（初音 Twixtor 4K，此前必 OOM）VLM 推理正常 tilt-orbit conf 0.792/66s；且 run55 全管线运动标注直接复活（独自升级2=zoom_in / 独自升级5=zoom_out 真实标签）。

**证据**：`output/evidence/enhance_drum_anchor_20260905/`（ab_result.json 含两轮数据+结论 / plan_diag_round2.txt / anchors.json / smoke_summary.json）；A/B 脚本 `tmp/ab_measure.py`、`tmp/plan_diag.py`（tmp 目录，阅后可归档入 scripts/）。

## 七、规则蒸馏引擎 v1 详细设计（E1-1 展开）

### 7.1 系统位置

```
【数据层】render_history.jsonl + decision_log + acceptance_log.jsonl（E0-4）
        ↓ scripts/distill_rules.py
【蒸馏层】轨迹归纳(AWM 思想) → 候选规则 → 回放验证(Voyager 原则) → 规则治理(ExpeL 机制)
        ↓ data/rules/ruleset.jsonl
【注入层】unified_edit.py 决策点按任务特征检索 top-k 规则注入（与 kb_loader 同模式）
        ↓
【优化层】GEPA 用评分函数+验收数据进化导演提示词与规则文本（E2-5，依赖本层成熟）
```

### 7.2 规则 schema（强制定义，防 run53 过拟合污染全局）

```json
{
  "rule_id": "R-2026-0007",
  "statement": "变速停顿镜头优先锚定 kick 重音，禁用 hihat onset",
  "form": "constraint | mapping | dosage | curve",
  "inject_point": "cut_anchor | effect_map | transition | speed_curve",
  "applicability": {
    "duration_range": [15, 45],
    "bgm_structure": ["build", "drop"],
    "style": ["燃向", "AMV"],
    "exceptions": "抒情段 BPM<90 时降级为建议"
  },
  "confidence": 0.82,
  "evidence": {
    "source_runs": ["run53"],
    "validation": "output/evidence/rule_validation_R-2026-0007/",
    "gate_score_delta": "+0.04 beat_hit_rate"
  },
  "votes": {"up": 3, "down": 0},
  "created": "2026-09-12",
  "last_confirmed": "2026-09-20"
}
```

### 7.3 转正流程（五步，对应证据闸门）

1. **归纳**：LLM 读成功 run 的 decision_log + 验收"采纳"记录，输出候选规则（附引用轨迹 ID）；
2. **反证检索**：在失败/差评 run 中检索该规则的反例，有强反例 → 降级或加 exceptions；
3. **回放验证**：在历史 run 素材上重放"有规则 vs 无规则"，评分差值落盘（闸门 2：首行证据）；
4. **转正**：差值显著且无强反例 → 写入 ruleset.jsonl，状态 active；否则 standby（闸门 5：分级）；
5. **退役**：连续 2 个新 run 中注入后评分无提升或验收差评 → 自动降权（ExpeL downvote 机制）。

### 7.4 与现有机制的关系

- `harvest_experience.py`（经验采集）继续负责 ledger 写入，蒸馏引擎是其**读侧消费者**；
- `core/experience_harvester.py` / `core/self_evolution_engine.py` 的既有结构保留，蒸馏引擎以独立脚本形态落地，成熟后再决定是否收编；
- `docs/漫剪内容层深度研究-从卡点到讲故事.md` 提出的三阶段叙事路线（direct_from_text → 素材-叙事匹配 → VLM 复核）：其第一阶段的 LLM 分镜接入与本引擎共享注入框架，规则库的 `inject_point` 预留 `narrative` 类型。
