## 二、事实核验：报告 vs 磁盘（差异清单）

> 方法：对报告中的关键数字逐条重跑磁盘命令。**下列 5 项与报告表述不一致**，整合时以磁盘为准。

### 2.1 未提交回归 F821 仍然存在（报告属实，且未修）

```
$ .venv/Scripts/python.exe -m ruff check --config ruff.toml .
scripts/unified_edit.py:199:29: F821 Undefined name `Optional`
Found 1 error.
```

- 该文件**全文无 `from typing import`**（`grep -c "from typing"` = 0），`Optional` 仅出现在 199 行。
- 属未提交工作区修改引入（`M scripts/unified_edit.py`），**阻塞 09-06 三批提交方案**。

### 2.2 参照集是 12 部，不是 13 部

```
$ ls data/reference_top/*.mp4 | wc -l   → 12
$ reference_gap_run61.json 内 refs 数组 → 12
$ data/reference_top/README.md          → "当前 12 条（目标 15+）"
```

报告 §1.1 与 §3.1 均写"13 部"，与磁盘、README、评分 JSON 三处不符。**实际 12 部**（目录内第 13 个文件是 README.md）。

### 2.3 "参照前三分位 0.8193"无法从落盘证据复现

- `reports/reference_gap_run61.json` 的 `deltas` 只含 `ref_mean / ref_min / ref_max`，**没有逐部分数、没有分位数**；
- `scripts/score_reference_gap.py` 源码只算 mean/min/max，**未实现分位数**；
- 0.8193 仅出现在 TASK_STATUS.md 与两份报告的叙述中，**无脚本产出物支撑**。

**影响**：评估报告的核心 S 级结论（"节奏引擎反超前三分位"）目前**证据链不闭合**。0.8455 > 0.8193 可能成立，但必须补一次 per-ref 落盘才能复核。

### 2.4 acceptance_log.jsonl 从未生成（GEPA 前置未满足）

- `data/evolution/` 实际只有 `render_history.jsonl`（28 条）与 `render_audit.jsonl`（**1 条**，run62）；
- `acceptance_log.jsonl` 不存在，git 历史中亦无记录（E0-4 的落盘路径从未被写入）。

**影响**：R8③ GEPA 的启动条件"acceptance_log 积累 ≥30 条"当前为 **0/30**；E1-1 的"≥5 条规则转正"也依赖它。**规则蒸馏这条线的瓶颈已不是机制，而是验收数据量。**

### 2.5 output 归档：报告称 43G，实际 24G，且 C1 内容为 0 文件

```
$ du -sh D:/AE-Data/output-archive-20260908/   → 24G
```

**影响**：C1 内容不可恢复。因 work/ 属可重生成过程产物，不影响资产安全，但**归档清单与实物不符**，若后续做体积核算需以 24G 为准。
