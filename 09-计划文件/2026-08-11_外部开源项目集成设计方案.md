## 二、各项目深度分析

### 2.1 VoidChecksum/adobe-mcp — Adobe 全套件 MCP Server

**核心架构**：
- Python 3.10+ 实现，通过 `pip install adobe-mcp` 一键安装
- COM 自动化（Windows）+ ExtendScript 双通道控制
- 支持 8 个 Adobe 应用：PS(13 工具) / AI(5) / PR(6) / AE(6) / ID(3) / Animate(2) / AME(1) / CH(1)
- MCP 标准协议，兼容 Claude Code / Codex CLI / Gemini CLI

**可复用模块**：
| 模块 | 复用价值 | 对应本项目缺陷 |
|------|---------|---------------|
| PS 13 工具集 | `ps_new_document` / `ps_layers` / `ps_filter` / `ps_export` 等 | D-02(PS Bridge)、D-05(texture)、D-06(LUT) |
| PR 6 工具集 | `pr_project` / `pr_sequence` / `pr_timeline` / `pr_export` | D-11~D-13(PR 协议不一致)、D-17(导出方案) |
| AE 6 工具集 | AE 渲染/脚本执行 | 增强现有 AE Bridge |
| COM 自动化层 | Windows COM 直接调用 Adobe，无需 CEP 面板 | D-18(CEP 扩展部署) |
| `adoberunjsx` / `adoberunjsxfile` | 通用 ExtendScript 执行器 | 统一所有 Adobe 脚本执行 |

**集成方案**：
```
现有架构                          adobe-mcp 集成
┌─────────────────┐              ┌─────────────────┐
│ Layer 2 Service  │ ──调用──→   │ adobe-mcp tools  │
│ (PS/PR/AE引擎)   │              │ (45 个标准化工具) │
└─────────────────┘              └────────┬────────┘
                                          │ COM + ExtendScript
                                          ▼
                                   Adobe 应用进程
```

**集成难度**：★★★☆☆（中等）
- 需 Windows 环境（已满足）
- COM 自动化要求 Adobe 软件运行中（与当前 Bridge 架构一致）
- Python 3.10+ 已满足
- 需评估 COM 接口与 AE 2025（非 2026）的兼容性

**依赖风险**：
- adobe-mcp 针对 Adobe 2026 开发，部分 COM 接口在 2025 可能缺失
- 项目较新（v0.1.0），API 可能不稳定

### 2.2 QwenLM/Qwen-MM-Plugins — 多模态模型插件集

**核心架构**：
- 7 大能力模块：core / video-memory / omni-av / video-edit / blender / freecad / edu-agent
- 每个模块 = skill（模型感知）+ 可选 MCP server（工具执行）
- 依赖 WSL2（Ubuntu）环境，`uvx` 管理 Python 依赖隔离
- API 类工具需 `DASHSCOPE_API_KEY`（视觉/OCR/ASR 等原生读图不需要）

**与现有项目的契合点**：

| Qwen-MM 能力 | 本项目对应模块 | 增强效果 |
|-------------|---------------|---------|
| **core**（动态分辨率读图/视频/文档/OCR/grounding/分割/ASR） | `vrs/video_effect_analyzer_v2.py` + `core/style_feature_extractor.py` | VRS 分析链路从"抽帧→API调用"升级为"原生多模态理解"，消除帧采样信息损失 |
| **video-memory**（长视频层级图记忆 → QA） | `vrs/` 分析链路 + 风格复刻方案方向A | 对长参考视频做层级记忆，支持"第 3 分钟那个转场是什么"式精确问答，直接生成 StyleSpec |
| **omni-av**（ASR+时间戳/时间字幕/事件计数/音乐标签） | `ae/beat_detector.py` + 字幕生成 | 增强节拍检测精度（音乐标签），ASR 带时间戳可直接生成字幕 |
| **video-edit**（编辑+生成工作流） | `ai/production_director.py` + `core/style_pipeline.py` | 视频编辑工作流增强，与风格复刻管线互补 |
| **blender**（22 工具驱动 Blender） | 方向机 D-19 BlenderEngine | 直接提供 Blender 控制能力，无需从零开发 BlenderEngine |
| **freecad**（14 工具参数化 CAD） | 方向机 Cinema4D 引擎 | 参数化建模能力补充 |

**与 `core/llm_gateway.py` 的集成点**：
```python
# 现有 TASK_PROVIDER_MAP 扩展
TASK_PROVIDER_MAP[TaskType.VISION_UNDERSTANDING] = ("qwen-mm-core", "vision")
# 新增任务类型
TaskType.VIDEO_MEMORY_QA      # 长视频记忆问答 → qwen-mm-video-memory
TaskType.OMNI_AV_UNDERSTAND   # 音视频理解 → qwen-mm-omni-av
TaskType.VIDEO_EDIT_PLAN      # 视频编辑规划 → qwen-mm-video-edit
```

**WSL2 环境搭建步骤**：
1. `wsl --install -d Ubuntu-22.04`（已在 Windows 25H2 上可用）
2. WSL2 内安装：`ffmpeg` / `uvx`（Python 包管理）/ `chromium`（可选）
3. 克隆 Qwen-MM-Plugins 到 WSL home 目录（非 `/mnt/c` 挂载盘）
4. 运行 `bash install.sh`（引导式安装：install → configure → verify）
5. 配置 `DASHSCOPE_API_KEY` 和 `SERPER_API_KEY`
6. 验证：`bash install.sh verify --check-system`

**集成难度**：★★★☆☆（中等）
- WSL2 环境搭建一次性工作
- 需确保 WSL2 内可访问 Windows 侧文件（用于分析 `D:\AE-Work\` 素材）
- API 调用走 DashScope，成本已在 llm_gateway 追踪体系内
- blender/freecad 为 thin client 模式，需 WSL2 内安装对应软件

**依赖风险**：
- 项目极新（2026-08-10 发布），API 可能快速变化
- WSL2 与 Windows 文件系统跨边界性能可能受限
- 部分能力（video-memory/omni-av/video-edit）Cookbook 仍为 TBD

### 2.4 inlife/nexrender — 数据驱动 AE 渲染引擎

**核心架构**：
- Node.js 构建，基于 `aerender` CLI
- JSON 作业配置：template（.aep 模板）+ assets（动态素材替换）+ actions（后处理）
- 支持素材替换（image/audio/video）+ 数据注入（text/property/expression）+ JSX 脚本执行
- REST API + Webhook 回调 + 分布式渲染（多 worker 节点）

**核心能力**：
```json
{
  "template": { "src": "file:///path/to/template.aep", "composition": "main" },
  "assets": [
    { "src": "image.jpg", "type": "image", "layerName": "background" },
    { "type": "data", "layerName": "title", "property": "Source Text", "value": "动态标题" }
  ],
  "actions": { "postrender": [{ "module": "@nexrender/action-encode", "output": "final.mp4" }] }
}
```

**与风格复刻方案的契合点**：
- 风格复刻方向A 的 StyleSpec JSON → nexrender assets 配置，实现"规格书驱动模板渲染"
- 漫剪/静止系的批量出片：一套 AE 模板 + N 套素材数据 = N 条差异化成片
- 其 `@nexrender/action-encode`（FFmpeg 后处理）与本项目 FFmpeg 输出服务一致

**集成方案**：
```
StyleSpec JSON ──转换──→ nexrender job JSON ──aerender──→ 成片
                          ↓
                    nexrender actions
                    (FFmpeg 转码/水印/上传)
```

**集成难度**：★★★☆☆（中等）
- 需 Node.js 环境（已安装）
- 需设计 AE 模板体系（.aep 模板 + 数据绑定图层命名规范）
- 与现有 Python 管线的桥接需开发适配层

**依赖风险**：
- nexrender 依赖 aerender CLI，与当前 AE 2025 兼容
- 模板设计需要 AE 侧配合（一次性工作）

### 2.5 mikechambers/adb-mcp — Adobe 通用 MCP（三层架构参考）

**核心架构**（三层代理模式）：
```
AI Agent ←→ MCP Server (Python) ←→ Command Proxy (Node.js) ←→ UXP Plugin (JS) ←→ Adobe App
```

**关键设计模式**：
- UXP 插件不能监听网络端口 → 通过"反向连接"解决（插件主动连接 Proxy）
- Command Proxy 维护与 UXP 插件的持久连接，转发 MCP 命令
- MCP Server 定义标准工具接口，AI Agent 通过 MCP 协议调用

**对本项目的参考价值**：
- 三层架构模式可应用于当前 Bridge 升级（文件轮询 → WebSocket/HTTP）
- "反向连接"设计解决 CEP/UXP 插件无法被动监听的网络限制
- 但其 UXP 路线在 AE 2025 尚不可用（AE UXP 仍在预览中），参考意义 > 直接复用

**集成难度**：★★★★☆（较高）— 架构升级需大规模重构，建议作为 P4 评估项

### 2.6 cloudflare/computer — Agent 运行时

**核心架构**：
- SQLite 虚拟文件系统（Durable Object 内）+ 可插拔执行后端
- 三种后端：沙箱容器（完整 Linux）/ Isolate Shell（轻量命令）/ Isolate JavaScript（ES 模块）

- 全部门控 + 审计日志

**对本项目的参考价值**：
| 设计理念 | 本项目应用场景 |
|---------|---------------|
| 持久文件系统 + 可插拔后端 | 流水线 Checkpoint 续传（中断后从最后成功节点恢复） |
| 执行环境隔离 | JSX 沙箱执行（安全 Agent 的前置基础设施） |
| 门控 + 审计 | 全链路操作审计（安全审计 Agent 的数据基础） |
| "需要电脑而非容器" | 9 引擎统一工作区（每个任务声明所需引擎，系统自动分配） |

**集成方案**：不直接集成代码，而是借鉴其架构理念：
1. 为 `workflow_orchestrator` 添加"持久工作区"概念（每个流水线实例一个工作目录）
2. Checkpoint 续传基于 SQLite 状态存储（替代当前文件轮询状态）
3. 安全 Agent 基于操作审计日志做阻断决策

**集成难度**：★★★★★（高）— 纯架构参考，需长期演进

### 2.8 DLR-RM/BlenderProc — 程序化 Blender 渲染管线 ⭐新增

**核心架构**：
- Python 库（`pip install blenderproc`），运行在 Blender 内置 Python 环境中
- 程序化场景构建：对象加载/创建 → 材质设置 → 灯光配置 → 相机定位 → 多通道渲染
- 支持格式：*.obj / *.ply / *.blend / *.fbx / ShapeNet / Haven / 3D-FRONT 等
- 渲染输出：RGB / 深度图 / 法线图 / 语义分割图 / 序列帧
- 数据写入：HDF5 容器 / COCO 标注 / BOP 标注

**关键能力**：
```python
import blenderproc as bproc
bproc.init()
obj = bproc.object.create_primitive("MONKEY")       # 程序化创建对象
light = bproc.types.Light()
light.set_location([2, -2, 0])
light.set_energy(300)                                # 程序化灯光
cam_pose = bproc.math.build_transformation_mat(...)  # 程序化相机
data = bproc.renderer.render()                       # 多通道渲染
bproc.writer.write_hdf5("output/", data)             # 输出
```

**与方向机 D-19 BlenderEngine 的契合点**：
| BlenderProc 能力 | 本项目应用场景 | 增强效果 |
|-----------------|---------------|---------|
| 程序化场景构建 | 自动生成 3D 背景/道具场景 | 无需手动建模，代码定义场景 |
| 物理定位（碰撞检测） | 物体自然摆放（如桌上散落物品） | 真实物理交互 |
| 多通道渲染（深度/法线/分割） | VRS 分析增强（深度图辅助理解场景层次） | 从 2D 分析升级到 2.5D |
| 相机采样 | 自动多视角渲染 | 批量生成不同角度的 3D 元素 |
| 材质程序化设置 | PBR 材质自动配置 | 真实感渲染 |

**集成方案**：
```
StyleSpec / 剧本参数
       ↓
BlenderProc Python 脚本（程序化构建 3D 场景）
       ↓
blender --background --python script.py
       ↓
PNG 序列 / 多通道图 → AE 合成（方向机 P2-09）
```

**与 Qwen-MM-Plugins blender 能力的互补关系**：
- Qwen-MM blender：22 个工具，侧重**交互式** Blender 控制（建模/材质/灯光/渲染）
- BlenderProc：侧重**程序化批量**渲染（代码定义场景 → 自动渲染）
- 两者互补：Qwen-MM 做"AI 理解 → 场景描述"，BlenderProc 做"场景描述 → 批量渲染"

## 七、关键决策点

1. **adobe-mcp 兼容性**：Phase 0-05 评估后决定——若 COM 在 AE 2025 不可用，仅集成 ExtendScript 工具子集
2. **Qwen-MM 优先级**：建议先集成 core + omni-av（最高 ROI），video-memory 和 video-edit 第二批
3. **nexrender vs 现有 aerender**：nexrender 不替代现有 aerender 调用，而是作为"批量个性化渲染"的增强通道
4. **cloudflare/computer 落地范围**：建议仅借鉴"持久工作区"和"审计日志"两个理念，不做代码级集成
5. **WSL2 文件策略**：素材复制到 WSL 内部 vs 跨边界访问——Phase 0 实测后决策
6. **BlenderProc vs Qwen-MM blender**：两者互补不冲突——Qwen-MM 做交互式控制，BlenderProc 做程序化批量渲染，同时集成
